## Admission and processing boundary

Operator-only issueInvitation generates 32 cryptographically random bytes and returns the secret once. D1 stores its SHA-256 hash, issuance/expiry, revocation and consumption metadata. Issuance is capped at ten records, including revoked/used records. Issue initially five, expand only within the approved pilot; the lifetime accepted-case cap remains ten including existing synthetic cases. Operator delivery is private and must not put invitations in URLs, logs, public channels or reports.

POST /api/benchmark/submissions requires x-benchmark-invitation. Possession is the authorization boundary: participant identity is NOT verified. Work email is contact metadata, not an identity proof. Each invitation admits one case. Exact idempotent retries recover the same case/run; a different key cannot reuse the invitation. Revocation prevents admission/retry; revokeCase separately denies a previously issued case capability. Secrets are password inputs held for submission and are not added to sessionStorage.

D1 batch and triggers atomically insert the submission, consume the valid unrevoked/unexpired invitation, enforce lifetime capacity and create permissions/run. Any transaction failure rolls back consumption and capacity. Native 5 requests/60 seconds limiter stays before intake parsing/writes/dispatch on the exact POST route. Counters remain local/permissive/eventually consistent; corporate NAT users share a budget and IPv6/distributed sources can evade it. Invitations and the D1 cap bound accepted work independently of IP. Invalid distributed requests can still incur edge and database-read costs. Observe request/error metrics and pause beta intake if abuse occurs; no paid WAF purchase is proposed.

BENCHMARK_AI_MODE is configured AI_DISABLED. The provider function fails closed unless a future explicit server setting AUTHORIZED_AI is introduced through separately approved activation. Submitter consent or a configured Groq key cannot enable processing in this beta. Deterministic checks, evidence classifications and human review remain. Existing optional-AI validation code is retained. Cached model candidates are ignored while disabled. Before upgrade, inventory any previously generated draft; server disablement cannot retroactively undo an earlier transfer. Existing external beta has admitted no external evidence according to the supplied baseline.

Case status polling now uses sequential 15/30/60/120-second backoff, skips hidden tabs, stops at terminal/released state or authorization denial, and prevents overlapping requests. It is not a server-side defense against someone building their own polling client.

## Complete approved deletion lifecycle

Operator functions are prepared; no public deletion endpoint or automatic purge exists. A protected operator execution channel must be agreed and rehearsed before launch. Every remote case deletion needs its own approval; policy/deployment approval does not authorize it.

1. Inventory all associated Workflow instances. For normal processing the instance ID equals the immutable run_id and the payload case/run must match; CorrectionWorkflow rejects a mismatched instance before evidence access. Dry-run queries every D1 run for the case. Independently reconcile dashboard/API instance inventory, including legacy/manual instances. The binding has no account-wide list operation; discovery outside the registered-run invariant is an operator step. Do not treat an API error as verified absence.
2. planDeletion reads metadata-only counts for all five tables, run IDs, last update and workflow states. Require terminal DB runs older than 30 days and complete/terminated instances. Active instances need separate authorized closure, never implicit termination. Use a fixed approved as-of time, exact case and plan hash. Wrong Workflow identity, changed plan or insufficient retention blocks execution.
3. deleteCase requires matching case/plan/policy/approval. Persist a D1 case fence first, then BLOCKED control/receipt metadata to external KV. Revalidate the approved plan after the fence. If anything changed, stop with the fence intact and request a new plan approval.
4. Processing, replay, dispatch, recovery and private reads consult the fence/control ledger. SQL INSERT/UPDATE fences protect all five evidence tables. A late dispatch rechecks the fence after creation and deletes its newly created instance when blocked. Privileged manual restarts remain an administrator responsibility; no administrator can be treated as an untrusted tenant.
5. For each exact registered run, call documented WorkflowInstance.delete(), which deletes stored state; termination alone is insufficient. Verify get(runId) fails specifically with instance.not_found. An unavailable delete API, wrong instance, permission/network error, or unverified disappearance stops before D1 purge. Independently verified expired instances can be supplied explicitly; never substitute a timeout or authorization failure.
6. Atomically insert the D1 receipt and purge events, findings, permissions, runs and submission, all scoped by case ID and terminal/latest-update guard. Case fence, invitation consumption and lifetime counts remain minimal control metadata; deletion does not reopen capacity. Verify zero rows, old capability denial, absent Workflow and unrelated control case intact; verify scheduled recovery cannot recreate the deleted run. Save PURGED receipt metadata outside D1. Ordinary SQL receipt mutation is prohibited; privileged schema changes and KV overwrites remain possible, so this is not an administrator-proof immutable vault.
7. Failure after fencing leaves access/processing denied. Preserve records for diagnosis. If Workflow deletion succeeded before a later failure, independently verify its absence and obtain/revalidate the exact plan for retry. Failure after D1 purge but before final KV receipt requires metadata verification and operator receipt reconciliation; never recreate evidence to repair a receipt.
8. Reconcile exports, provider logging/history and client copies under approved scope. Do not expose evidence/capabilities in diagnostic output. Retain minimal control records at least through all authorized restoration paths; exact retention for these pseudonymous records requires controller approval. No automatic expiry is configured.

Cloudflare documents that delete removes instance state and stops running execution without rollback handlers: https://developers.cloudflare.com/workflows/build/workers-api/. Logical API absence is not proof of immediate removal from every provider backup.

## Restore safety — mandatory closed restore window

KV is eventually consistent; absence in a new region can be cached. It is not a globally atomic revocation service. D1 SQL fences are the normal live-write boundary. After any D1 restore, keep all beta public/private routes AND Workflow recovery disabled at the operator-controlled infrastructure level until reconciliation and multi-location denial checks finish. Do not rely on KV alone during restoration and do not restore/roll back the control ledger alongside D1.

Reapply migrations to the restored image as needed. reconcileControls replays external case fences and invitation revocations, and keeps accepted capacity monotonic against restored submissions plus external case/admission identities. Consumed invitations cannot create a new case even with the old idempotency key when their original saved case is absent. Ledger case fences also deny restored original capabilities and cached processing. Re-purge restored deleted evidence/Workflow instances using a separately approved plan before reopening. Verify revoked invitations, original links, all deletion identities, capacity, unaffected control case, and recovery behavior. Review issuance records and delivery history so a pre-issuance restore cannot silently authorize additional invitations.

Backfill pre-M1.5 D1 revoked cases into the external ledger using the prepared backfillLegacyRevocations helper only after specific approval. Its queries include IDs only. Existing remote revocations were not modified/backfilled during preparation. Preserve owner-held minimal control-ledger exports outside the D1 restore domain; assign access and retention. If the ledger is missing/incomplete, keep beta closed. Before any restore, confirm its backup provenance and approved deletion ledger. Rotate case signing authority under separately approved credential handling if denial completeness cannot be established; do not disclose the secret.

D1 Time Travel residuals depend on the actual plan (documented Free seven days/Paid thirty days). Verify the actual beta plan and other export retention before disclosure: https://developers.cloudflare.com/d1/reference/time-travel/. No restore or remote deletion was performed here.
